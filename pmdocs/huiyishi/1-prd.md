## 2. 页面与功能设计

### 2.1 P-001 会议室列表页

#### 目的
用户查看所有会议室及其实时状态，快速找到可用的会议室。

#### UI元素
- 页面标题："会议室列表"
- 筛选区域：
  - 容量筛选：下拉框（1-10人、11-20人、21-50人、50人以上）
  - 位置筛选：文本输入框（支持模糊搜索）
  - "重置"按钮
- 会议室列表（卡片式或表格式）：
  - 会议室名称
  - 容量（人数）
  - 位置
  - 实时状态标签（空闲/已预订）
  - "预订"按钮
- 分页控件（每页20条）
- 顶部导航栏（会议室列表、创建预订、我的预订、用户白名单管理[管理员]）

#### 交互说明
- 用户选择筛选条件后，列表自动刷新
- 点击"预订"按钮跳转到创建预订页（P-003），自动选中该会议室
- 状态标签根据当前时间实时更新（空闲/已预订）
- 分页切换时保持筛选条件

#### 空态/异常态
- **空态**：无会议室时显示"暂无会议室，请联系管理员添加"
- **筛选无结果**：显示"未找到符合条件的会议室"
- **加载失败**：显示"加载失败，请刷新重试"

### 2.2 P-002 会议室管理页

#### 目的
管理员添加、编辑、删除会议室，维护会议室信息。

#### UI元素
- 页面标题："会议室管理"
- 操作按钮：
  - "添加会议室"按钮
- 会议室列表（表格式）：
  - 会议室名称
  - 容量
  - 位置
  - 操作列："编辑"按钮、"删除"按钮
- 分页控件（每页20条）
- 添加/编辑会议室对话框：
  - 会议室名称输入框（必填，2-50字符）
  - 容量输入框（必填，正整数，1-500）
  - 位置输入框（选填，0-200字符）
  - "取消"按钮、"保存"按钮
- 删除确认对话框：
  - 提示文字："确定要删除该会议室吗？"
  - "取消"按钮、"确定"按钮
- 有未来预订时的警告对话框：
  - 提示文字："该会议室有未来预订，删除将同时删除所有预订记录，确定继续吗？"
  - "取消"按钮、"确定"按钮

#### 交互说明
- 点击"添加会议室"按钮打开添加对话框
- 点击"编辑"按钮打开编辑对话框，回显当前会议室信息
- 点击"删除"按钮显示删除确认对话框
- 删除前检查是否有未来预订，如有则显示警告对话框
- 会议室名称重复时显示错误提示
- 保存成功后刷新列表并显示成功提示

#### 空态/异常态
- **空态**：无会议室时显示"暂无会议室，点击添加"
- **名称重复**：显示"会议室名称已存在"
- **删除失败**：显示"删除失败，请重试"

### 2.3 P-003 创建预订页

#### 目的
用户创建会议室预订，选择会议室、日期、时间段，输入会议信息。

#### UI元素
- 页面标题："创建预订"
- 预订表单：
  - 会议室选择：下拉框（从会议室列表加载）
  - 日期选择：日期选择器（不允许选择过去日期）
  - 时间段选择：时间选择器（按小时，工作时间段8:00-20:00）
  - 用户名选择：下拉框（从用户白名单加载，白名单为空时为文本输入框）
  - 会议主题输入框（必填，2-100字符）
  - 参会人输入框（选填，多个参会人用逗号分隔）
  - "取消"按钮、"提交"按钮
- 冲突提示对话框：
  - 提示文字："该时间段已被预订，请选择其他时间"
  - 显示冲突的预订时间段
  - "确定"按钮
- 预订成功提示：
  - 提示文字："预订成功！会议室：XXX，日期：XXX，时间段：XXX"
  - 3秒后自动消失
  - 自动跳转到"我的预订"页（P-004）

#### 交互说明
- 选择会议室后，显示该会议室的容量和位置
- 选择日期后，时间段选择器只显示可用时间段（排除已预订的时间段）
- 提交时检测时间冲突，如有冲突显示冲突提示对话框
- 单次预订最长不超过8小时
- 白名单为空时，用户名输入框为文本输入（临时方案）
- 预订成功后显示成功提示，3秒后自动跳转到"我的预订"页

#### 空态/异常态
- **无会议室**：显示"暂无会议室，请先添加会议室"
- **无可用时间段**：显示"该日期所有时间段已被预订"
- **冲突**：显示冲突提示对话框
- **提交失败**：显示"预订失败，请重试"

---

### 2.4 P-004 我的预订页

#### 目的
用户查看自己的所有预订记录，取消预订。

#### UI元素
- 页面标题："我的预订"
- 筛选区域：
  - 日期筛选：日期选择器
  - "重置"按钮
- 预订列表（卡片式或表格式）：
  - 会议室名称
  - 日期
  - 时间段
  - 会议主题（用户本人查看时解密显示）
  - 参会人（用户本人查看时解密显示）
  - 状态标签（已结束/今天/待开始）
  - "取消"按钮（仅待开始的预订显示）
- 分页控件（每页20条）
- 取消确认对话框：
  - 提示文字："确定要取消该预订吗？"
  - "取消"按钮、"确定"按钮
- 已开始预订取消提示对话框：
  - 提示文字："该预订已开始，无法取消"
  - "确定"按钮
- 取消成功提示：
  - 提示文字："取消成功"
  - 3秒后自动消失

#### 交互说明
- 列表按日期倒序排列
- 过期的预订标记为"已结束"，今天的预订标记为"今天"，未来的预订标记为"待开始"
- 已开始的预订不显示"取消"按钮
- 点击"取消"按钮显示取消确认对话框
- 取消操作需要二次确认
- 取消成功后刷新列表并显示成功提示

#### 空态/异常态
- **空态**：无预订时显示"暂无预订记录"
- **筛选无结果**：显示"未找到符合条件的预订"
- **加载失败**：显示"加载失败，请刷新重试"

## 3. 核心交互流程

### 3.1 预订流程

```
用户 → 会议室列表页 (P-001)
  → 点击"预订"按钮
  → 创建预订页 (P-003)
  → 选择会议室、日期、时间段
  → 输入用户名（从白名单选择或输入）
  → 输入会议主题、参会人
  → 点击"提交"按钮
  → 系统检测冲突 (FR-006)
    → 有冲突 → 显示冲突提示对话框 → 用户修改时间 → 重新提交
    → 无冲突 → 保存预订记录 (FR-005)
  → 显示预订成功提示 (FR-007)
  → 自动跳转到我的预订页 (P-004)
```

### 3.2 取消预订流程

```
用户 → 我的预订页 (P-004)
  → 查看预订列表
  → 点击"取消"按钮
  → 显示取消确认对话框
  → 点击"确定"按钮
  → 检查预订是否已开始
    → 已开始 → 显示已开始提示对话框 → 无法取消
    → 未开始 → 删除预订记录 (FR-009)
  → 显示取消成功提示
  → 刷新预订列表
```

### 3.3 会议室管理流程

```
管理员 → 会议室管理页 (P-002)
  → 添加会议室
    → 点击"添加会议室"按钮
    → 输入会议室信息
    → 点击"保存"按钮
    → 检查名称是否重复
      → 重复 → 显示错误提示
      → 不重复 → 保存 (FR-001)
    → 刷新列表
  → 编辑会议室
    → 点击"编辑"按钮
    → 修改会议室信息
    → 点击"保存"按钮
    → 检查名称是否重复
      → 重复 → 显示错误提示
      → 不重复 → 更新 (FR-002)
    → 刷新列表
  → 删除会议室
    → 点击"删除"按钮
    → 检查是否有未来预订
      → 有 → 显示警告对话框 → 二次确认 → 删除 (FR-003)
      → 无 → 显示确认对话框 → 确认 → 删除 (FR-003)
    → 刷新列表
```

## 4. 技术选型

### 4.1 方案一：React + Ant Design + Node.js + Express + MySQL

#### 前端
- **框架**：React 18
- **UI库**：Ant Design 5
- **HTTP客户端**：Axios
- **状态管理**：React Context API / Redux
- **路由**：React Router 6

#### 后端
- **运行时**：Node.js 18+
- **Web框架**：Express 4
- **ORM**：Sequelize / TypeORM
- **数据库**：MySQL 8.0
- **加密库**：crypto (Node.js内置)
- **日志库**：Winston / Morgan

#### 优点
- React + Ant Design生态成熟，组件丰富，开发效率高
- Node.js + Express轻量级，适合快速开发
- MySQL企业常用，性能好，事务支持完善
- 团队可能熟悉该技术栈

#### 缺点
- MySQL需要单独安装和配置
- Node.js单线程，高并发需要cluster模式
- Ant Design组件体积较大

#### 适用场景
- 企业已有MySQL数据库
- 团队熟悉React/Node.js技术栈
- 需要快速开发MVP

---

### 4.2 方案二：Vue 3 + Element Plus + Node.js + Express + PostgreSQL

#### 前端
- **框架**：Vue 3
- **UI库**：Element Plus
- **HTTP客户端**：Axios
- **状态管理**：Pinia
- **路由**：Vue Router 4

#### 后端
- **运行时**：Node.js 18+
- **Web框架**：Express 4
- **ORM**：Prisma / TypeORM
- **数据库**：PostgreSQL 14
- **加密库**：crypto (Node.js内置)
- **日志库**：Winston / Morgan

#### 优点
- Vue 3 Composition API代码组织性好
- Element Plus组件丰富，适合企业应用
- PostgreSQL功能强大，支持JSON字段
- Prisma ORM类型安全，开发体验好

#### 缺点
- PostgreSQL学习曲线略陡
- Element Plus组件体积较大
- 团队可能不熟悉Vue技术栈

#### 适用场景
- 企业已有PostgreSQL数据库
- 团队熟悉Vue技术栈
- 需要更灵活的数据类型（JSON字段）

---

### 4.3 方案三：React + Ant Design + Python + FastAPI + SQLite

#### 前端
- **框架**：React 18
- **UI库**：Ant Design 5
- **HTTP客户端**：Axios
- **状态管理**：React Context API / Redux
- **路由**：React Router 6

#### 后端
- **运行时**：Python 3.10+
- **Web框架**：FastAPI
- **ORM**：SQLAlchemy
- **数据库**：SQLite
- **加密库**：cryptography
- **日志库**：logging

#### 优点
- SQLite无需单独安装，零配置
- FastAPI性能好，自动生成API文档
- Python生态丰富，加密库成熟
- 适合快速原型开发

#### 缺点
- SQLite性能有限，不适合高并发
- SQLite不支持多进程写入
- 50人并发可能成为瓶颈
- 企业内网可能已有其他数据库

#### 适用场景
- 快速原型验证
- 无企业数据库限制
- 并发要求不高（<20人）

---

### 4.4 技术选型建议

**推荐方案一（React + Ant Design + Node.js + Express + MySQL）**，理由：
1. 符合"使用企业现有数据库"约束（待确认数据库类型）
2. React + Ant Design生态成熟，开发效率高
3. MySQL性能好，支持50人并发
4. 3天MVP开发时间紧，成熟技术栈降低风险

**注意事项**：
- 需要确认企业现有数据库类型（MySQL/PostgreSQL/SQL Server）
- 如果企业数据库是PostgreSQL，选择方案二
- 如果企业数据库是SQL Server，需要调整后端技术选型（.NET Core）

## 5. 数据模型

### 5.2 索引设计

| 表名 | 索引名 | 字段 | 类型 | 说明 |
|------|--------|------|------|------|
| Room | idx_name | name | UNIQUE | 会议室名称唯一索引 |
| Booking | idx_room_date | room_id, date | INDEX | 会议室+日期索引（冲突检测） |
| Booking | idx_user_name | user_name | INDEX | 用户名索引（查询我的预订） |
| Booking | idx_date | date | INDEX | 日期索引（按日期筛选） |
| UserWhitelist | idx_username | username | UNIQUE | 用户名唯一索引 |

## 7. 需求矛盾或缺失

### 7.1 需求矛盾

**矛盾1：管理员角色定义不明确**
- **问题描述**：0-req.md提到"管理员"角色，但没有明确如何区分管理员和普通用户
- **影响**：无法实现权限控制（管理员才能访问P-002和P-005）
- **解决方案**：管理员有专门的管理员账户，通过登录时选择角色或环境变量配置管理员用户名

### 7.2 需求缺失

**缺失1：管理员认证方式**
- **问题描述**：0-req.md明确不做"用户认证系统"，但管理员和普通用户需要区分权限
- **影响**：无法实现权限控制
- **解决方案**：管理员有专门的管理员账户，在用户白名单中标记admin角色

**缺失2：会议室状态更新逻辑**
- **问题描述**：FR-004要求"显示会议室的实时状态（空闲/已预订）"，但没有明确状态如何计算
- **影响**：状态显示逻辑不明确
- **解决方案**：会议室状态为对应时间对应状态（根据当前时间和预订记录计算）

**缺失3：预订时长限制验证时机**
- **问题描述**：FR-005 AI补充提到"单次预订最长不超过8小时"，但没有明确验证时机（前端验证？后端验证？）
- **影响**：验证逻辑不明确
- **解决方案**：前后端都需要验证
